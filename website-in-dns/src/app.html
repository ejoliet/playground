A small world, inside a TXT record.

Pages, pictures, and a little play. This entire field station fits inside the Domain Name System.

Once this document is reconstructed, its pages run entirely in your browser. The loader retrieves compressed chunks over DNS-over-HTTPS; there is no HTTP content origin.

One address, many fragments

A manifest identifies numbered TXT records. The browser joins their base64 payloads, checks a SHA-256 digest, decompresses the document, and opens it in a sandbox. The stylesheet, these words, images, and game code all travel together.

A useful constraint

DNS is excellent at answering small, cacheable questions. A website asks it to become a distribution system. The experiment is about the point where those two jobs stop agreeing.

Images are bytes, too

The PNG is embedded with a data URL. That adds base64 expansion before the whole document is compressed. The curve is inline SVG, so it needs no separate lookup. Neither approach changes DNS’s record-size limits: large images simply require more chunks.

Field notebook

A searchable pocket guide to the compromises.


255 bytes is a string limit

A TXT resource record can contain several character-strings. Each string has a one-byte length field and can hold at most 255 bytes. Joining the strings in one record is correct; joining unrelated records without an ordering protocol is not. A DNS message has its own size ceiling, and DNS providers can impose much smaller limits.

Small packets, long journeys

Classic DNS over UDP allowed 512-byte messages. EDNS extends that, but fragmentation makes large UDP answers fragile. Recursive resolvers may retry truncated answers over TCP. DNS-over-HTTPS removes the browser’s UDP constraint, not the resolver’s upstream constraints. More chunks trade large answers for more round trips.

Caching is part of the data model

A TTL is a maximum freshness interval, not a promise that every cache retains an entry that long. Use immutable chunk names for each release and update the manifest last. Keep old chunks through the manifest TTL and a safety margin. Negative answers are cached too: looking up a name before publishing it can delay the first successful load.

Compression before encoding

Gzip works well for repeated HTML and CSS. Compress the document before base64 encoding it for DNS. Base64 needs four characters for every three bytes, rounded up. A photograph may compress little more than its original image format; a short SVG diagram can compress dramatically.

A hash is not an identity

A manifest hash detects corrupted or missing chunks. If an attacker can replace both the manifest and chunks, that hash alone proves nothing about the publisher. The loader can pin the manifest digest. It also isolates the fetched app in an iframe with scripts allowed but no same-origin privileges, forms, or top navigation. A content security policy blocks arbitrary network requests.

What this cannot replace

There is no server-side session, private account, multiplayer state, or transactional database here. Anyone can read published TXT records. The game is local. DNS control-plane credentials must never enter browser code. Publishing through a DNS API is an authoring operation, not a content server needed by readers.

Read the result carefully

Status 0 means NOERROR; 3 is NXDOMAIN; 2 is SERVFAIL; 5 is REFUSED. An HTTP success does not guarantee a successful DNS answer. A decreasing TTL is evidence consistent with caching, but a fast response by itself does not prove a cache hit.

The timing includes browser, HTTPS connection, resolver, and network costs. Repeating the same name cannot guarantee a cold recursive cache. This inspector does not claim to measure that.
